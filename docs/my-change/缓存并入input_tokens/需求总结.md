# 缓存并入 input_tokens 需求总结

> 说明：本文基于当前 **待提交 git 改动**整理，已**排除** `docs/my-change/部署文档.md`。

## 一、这次需求要解决什么问题

当前 Claude Code/Anthropic 一类响应里，`usage` 往往会拆出几类 prompt 侧 token：

- `input_tokens`
- `cache_read_input_tokens`
- `cache_creation_input_tokens`

但在某些接入场景里，业务希望把“缓存命中的 token”也视为普通输入消耗，不再单独暴露 cache usage 字段。也就是说：

1. **渠道级可配置**是否开启“缓存并入 input_tokens”
2. 开启后，响应里的 cache usage 字段不再保留
3. 下游看到的是“prompt/input 侧总量”，而不是“普通输入 + cache 读 + cache 写”的拆分结果
4. 如果同时开启“模拟缓存（simulate cache）”，要先做“缓存并入 input_tokens”，再决定是否重新伪造 cache usage

从当前实现看，这个需求是围绕 **Claude Code 渠道**做的，不是全局所有渠道统一生效。

---

## 二、功能需求拆解

## 1）新增 Claude Code 渠道级开关

在渠道配置里新增 `mergeCacheTokensIntoInput` 开关，仅对 `claudecode` 类型渠道生效。

用户可以在前端渠道编辑弹窗中直接勾选“缓存 Token 并入 Input”。该配置会进入渠道 `settings`，并通过 GraphQL 查询/修改接口读写。

### 预期行为

- `claudecode` 渠道：允许配置并生效
- 非 `claudecode` 渠道：即便前端曾残留过该字段，也应在提交时清理，不向后端传无效 Claude Code 专属配置

---

## 2）开启后，响应里的 cache usage 字段要被清空

当开关打开时，响应里的这些字段要被清零：

- `cache_read_input_tokens`
- `cache_creation_input_tokens`
- `write_cached_5m`
- `write_cached_1h`

在 AxonHub 当前 usage 结构里，对应的是 `PromptTokensDetails` 里的：

- `CachedTokens`
- `WriteCachedTokens`
- `WriteCached5MinTokens`
- `WriteCached1HourTokens`

并且会重新计算：

- `TotalTokens = PromptTokens + CompletionTokens`

### 关键语义

从产品需求表达上，这个能力叫“缓存并入 input_tokens”；
从当前代码实现上，实际效果是：

- **不再单独保留 cache usage 子字段**
- prompt/input 侧消耗按普通输入理解
- 最终对外返回和落库的 usage，不再携带原始 cache 分项

---

## 3）必须同时支持非流式和流式响应

该能力不能只改普通 JSON 响应，还必须覆盖 SSE/流式响应。

### 非流式

在 `OnOutboundLlmResponse` 阶段，如果开启该开关，则直接处理 `response.Usage`，清空 cache usage 字段。

### 流式

在 `OnOutboundLlmStream` 阶段包装 stream，对每个带 usage 的 chunk 执行相同处理。这样客户端在流式过程中看到的 usage 和最终落库的 usage 才一致。

---

## 4）即使拿不到 conversation ID，也要支持“仅做并入，不做模拟缓存”

之前 simulate-cache 逻辑更依赖 conversation/session 维度来伪造缓存使用情况。

这次需求新增了一个重要边界：

- 如果只是“缓存并入 input_tokens”开启
- 即使没有 conversation ID
- 也应该继续执行“清空 cache usage 字段”的逻辑

也就是说：

- **simulate cache** 依赖会话识别
- **merge cache tokens into input** 不应该被会话识别卡死

---

## 5）和 simulate cache 的执行顺序必须明确

这次不是替代 simulate cache，而是和它并存。

要求是：

1. **先**把上游真实返回的 cache usage 字段清掉（并入普通 input 语义）
2. **再**根据 AxonHub 自己的 simulate-cache 逻辑，决定是否重新伪造一套 cache usage

这样做的原因是：

- 避免“上游真实 cache 字段”和“AxonHub 伪造 cache 字段”混在一起
- 保证 simulate cache 的输入基线统一
- 避免最终 usage 里同时混入两套语义来源不同的 cache 数据

测试也专门覆盖了“merge 先执行，再 simulate”的场景。

---

## 6）持久化/usage_log 必须记录“修正后的最终 usage”，不能记录修正前的原始 usage

这是本次需求里非常关键但容易漏掉的一点。

如果只改返回给客户端的 usage，而不改持久化逻辑，会出现：

- 客户端看到的是“已并入 input 后的 usage”
- 数据库 `usage_log` 里存的却还是“原始 cache usage”

这样前后端、账单、请求详情都会不一致。

因此这次改动额外补了：

### 非流式请求

- 不再在过早阶段立即写 usage log
- 改成在更靠后的响应持久化阶段，使用最终修正后的 `llmResp.Usage` 去写 usage log

### 流式请求

- 新增 `FinalStreamUsage` 状态
- 在流式 chunk 被中间件修正后，抓取最后一次有效 usage
- 聚合落库时优先使用 `FinalStreamUsage`
- 避免仍然使用 transformer 聚合出来的原始 meta usage

这部分改动的本质，是为了保证：

> **客户端看到什么 usage，数据库最终就记录什么 usage。**

---

## 7）该能力仅对 Claude Code 渠道生效

后端注入 metadata 时，已经明确加了渠道类型判断：只有 `claudecode` 渠道，才会把这组 `cc_*` 元数据写入请求。

对应要求就是：

- 这个开关是 Claude Code 专属能力
- 不能误作用到普通 OpenAI、Gemini、Anthropic 兼容渠道
- 即使 settings 里有残留字段，非 Claude Code 也应该按关闭处理

---

## 三、数据流（按当前实现）

```text
前端渠道配置（勾选“缓存 Token 并入 Input”）
    ↓
GraphQL / ChannelSettings 保存 mergeCacheTokensIntoInput
    ↓
Orchestrator 根据当前选中的 claudecode 渠道，把配置注入 request.Metadata
    ↓
PromptCacheDisguise 中间件读取 metadata，记录 request marker
    ↓
收到上游 usage 后：
    1. 如果开启 mergeCacheTokensIntoInput，先清空 cache usage 字段
    2. 如果同时满足 simulate-cache 条件，再伪造新的 cache usage
    ↓
最终 usage 返回客户端
    ↓
同一份最终 usage 被写入 request / request_execution / usage_log 相关持久化链路
```

## 五、这批改动可以提炼成的功能验收标准

如果把这次需求写成验收口径，可以整理成下面几条：

1. **渠道配置层面**
   - Claude Code 渠道支持配置 `mergeCacheTokensIntoInput`
   - 查询、创建、更新、表单回显都完整支持该字段

2. **运行时行为层面**
   - 开启后，响应里的 cache usage 子字段被清空
   - 非流式和流式都生效
   - 无会话 ID 时，merge-only 仍然生效
   - 非 Claude Code 渠道不生效

3. **与 simulate cache 的协作层面**
   - 如果同时开启 simulate cache，先执行 merge，再伪造 simulate-cache usage
   - 不允许上游真实 cache usage 和 AxonHub 伪造 cache usage 混用

4. **持久化一致性层面**
   - usage_log 保存的是最终修正后的 usage
   - 客户端看到的 usage 与落库 usage 一致

## 六、可以如何理解这次改动的本质

表面上看，这次只是“多了一个开关”。

但从代码改动范围看，它实际上包含了三层事情：

1. **配置层**：让用户能在 Claude Code 渠道上声明“不要暴露真实 cache usage 分项”
2. **运行时层**：在响应处理中真正执行 merge，并和 simulate cache 排好顺序
3. **持久化层**：保证最终修正过的 usage 能被正确落库，避免页面显示与账单记录不一致

所以这不是单纯的 UI 字段新增，而是一次**从配置、编排、中间件到持久化链路的完整打通**。
