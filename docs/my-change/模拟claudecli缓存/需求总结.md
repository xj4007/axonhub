# 模拟 Claude CLI 缓存（Simulate Cache）

## 需求描述

Claude Code 客户端在与 Anthropic API 交互时，响应中会包含 prompt cache usage 信息（`cache_creation_input_tokens`、`cache_read_input_tokens` 等字段）。当请求通过 AxonHub 网关转发到非 Anthropic 的上游（或上游不返回缓存信息）时，Claude Code 客户端会因为缺少这些字段而出现异常行为或降级体验。

本需求在 AxonHub 的 Claude Code 渠道上新增"模拟缓存"功能：根据同一会话的 prompt token 变化趋势，在响应的 `usage` 中伪造合理的 cache usage 数据，使 Claude Code 客户端认为上游启用了 prompt caching。

### 核心规则

#### 规则 1：哪些请求会被处理（资格判定）

不是所有经过 AxonHub 的请求都会被伪造缓存，必须同时满足以下三个条件：

- **渠道开关打开**：该 Claude Code 渠道的 `simulateCache` 设置为 `true`（在前端渠道编辑页面勾选"模拟缓存"）
- **是 Claude Code 主请求**：请求的 system prompt 中包含以 `x-anthropic-billing-header:` 开头且含 `cc_version=` 的文本。这是 Claude Code 客户端的特征标识，普通 API 调用不会有这个
- **不是子代理请求**：Claude Code 内部会用 haiku 模型发一些轻量子任务（比如摘要、分类），这些请求的特征是：模型名包含 "haiku" 且缺少 tools 列表或缺少 system prompt。这类请求不伪造缓存

简单说：只有「渠道开了开关 + 真正的 Claude Code 主对话请求」才会触发伪造。

#### 规则 2：怎么识别"同一个会话"

伪造缓存需要知道"这个请求属于哪个会话"，因为缓存是按会话维度累积的。会话 ID 的提取按优先级依次尝试：

1. 请求 metadata 中的 `thread_id` / `trace_id` / `session_id` / `request_id`
2. 请求 metadata 中的 `user_id`（如果是 Claude Code 格式的 user_id，会从中提取 `_session_` 后面的部分作为会话 ID）
3. 请求 header 中的 `AH-Thread-Id` / `AH-Trace-Id` / `Session_id`
4. 请求的 `requestID`
5. context 中的 session ID

只要命中任意一个就用它作为会话 ID。如果全部都没有，则不伪造。

#### 规则 3：伪造算法（核心）

Anthropic 真实的 prompt cache 机制是这样的：当你多轮对话时，之前发过的 system prompt 和历史消息会被缓存，后续请求只需要为新增部分付费。响应的 usage 中会体现三个数字：

- `input_tokens`：没有被缓存的新 token（需要全价计费）
- `cache_creation_input_tokens`：本次新写入缓存的 token（首次缓存，计费较贵）
- `cache_read_input_tokens`：从缓存中读取的 token（计费便宜）

三者之和 = `prompt_tokens`（总的 prompt token 数）。

我们的伪造算法模拟这个行为。系统会为每个会话维护一个状态，记录上一次请求的 `prompt_tokens` 值（记为 `last`），然后根据当前请求的 `prompt_tokens`（记为 `current`）来决定怎么拆分：

**场景 A：会话的第一次请求（没有历史状态）**

```
假设 current = 1000

cache_creation = 1000 × 90% = 900   （模拟"首次把 prompt 写入缓存"）
input_tokens   = 1000 - 900 = 100   （剩余部分算作普通输入）
cache_read     = 0                   （第一次没有可读的缓存）
```

含义：第一次对话时，大部分 token 被"写入缓存"，少量是普通输入。这符合真实行为——首次请求没有缓存可读，全部都是新的。

**场景 B：后续请求，token 正常增长，增量 ≥ 110（`MIN_CACHE_CREATION` 常量）**

```
假设 last = 1000, current = 1300, delta = 300

cache_read     = 1000              （上次的全部 token 都"从缓存读取"）
cache_creation = 300 - random(0~5) （新增部分几乎全部"写入缓存"）
input_tokens   = random(0~5)       （极少量随机 token 算作普通输入）
```

含义：对话继续时，之前的内容已经在缓存里了（cache_read），新增的消息内容被写入缓存（cache_creation），只有极少量 token 不走缓存。random(0~5) 是用 FNV hash 基于会话 ID + 序号生成的确定性随机数，同样的输入永远产生同样的结果。

为什么要有 110 的阈值？因为真实的 Anthropic cache 有最小写入粒度，增量太小时不会触发 cache creation。

**场景 C：后续请求，token 正常增长，但增量 < 110**

```
假设 last = 1000, current = 1050, delta = 50

cache_read     = 1000   （上次的全部 token 从缓存读取）
cache_creation = 0      （增量太小，不够触发缓存写入）
input_tokens   = 50     （新增部分全部算作普通输入）
```

含义：用户只发了一条很短的消息，增量不够触发缓存写入，所以新增部分全部是普通输入。

**场景 D：token 回退（current < last）**

```
假设 last = 1000, current = 600

cache_creation = 600 × 10% = 60    （少量重新写入缓存）
cache_read     = 600 - 60 = 540    （大部分从缓存读取）
input_tokens   = 0                 （没有新增输入）
```

含义：这种情况发生在用户开了新对话或者上下文被截断。token 总量变少了，但大部分内容仍然在缓存中，只有少量需要重新写入。

**归一化保护**：最终 `normalizedForgedUsage` 函数会确保 `input_tokens + cache_creation + cache_read = prompt_tokens`，如果因为整数运算导致不等，会自动调整（优先削减 input_tokens，其次 cache_creation，最后 cache_read）。

#### 规则 4：缓存类型（写入哪个字段）

Anthropic 的 cache 有两种 TTL 类型，对应响应中不同的字段：

- `ephemeral_5m_input_tokens`（默认）：缓存 5 分钟，伪造的 cache_creation 值写入 `WriteCached5MinTokens` 字段
- `ephemeral_1h_input_tokens`：缓存 1 小时，伪造的 cache_creation 值写入 `WriteCached1HourTokens` 字段

两种模式互斥，选了 5m 就不会写 1h 字段，反之亦然。在前端渠道配置页面通过单选按钮选择。

#### 规则 5：渠道级独立配置

每个 Claude Code 渠道可以独立设置：

- 是否启用模拟缓存（`simulateCache` 开关）
- 使用哪种缓存类型（`simulateCacheMode` 单选）

配置存储在渠道的 `settings` JSON 字段中，通过 GraphQL API 读写。编排器在每次请求转发时，会把当前选中渠道的配置注入到 request metadata 中（`cc_simulate_cache_enabled` / `cc_simulate_cache_mode`），中间件据此决定是否伪造。

#### 规则 6：会话状态管理

会话状态（上次的 prompt_tokens、更新时间、序号）存储在内存中，使用 LRU + TTL 策略管理：

- TTL = 45 分钟：超过 45 分钟没有新请求的会话状态会被清理
- 最大条目数 = 4096：超出时淘汰最久未使用的会话
- 清理间隔 = 3 分钟：每 3 分钟扫描一次过期条目

这意味着如果用户 45 分钟内没有发新消息，下次请求会被当作"新会话的第一次请求"处理（场景 A）。

#### 规则 7：流式响应处理

对于流式（SSE）响应，中间件会包装原始 stream，在每个包含 usage 的 chunk 上应用伪造逻辑。如果连续多个 chunk 的 `prompt_tokens` 相同（常见于流式传输中重复发送 usage），会复用上一次的伪造结果，避免重复计算。

## 数据流

```
Claude Code Client
    │
    ▼
AxonHub API (Inbound)
    │
    ▼  OnInboundLlmRequest — 提取会话 ID，创建 requestMarker
Pipeline Middleware: PromptCacheDisguise
    │
    ▼  TransformRequest — orchestrator 注入 cc_simulate_cache_* metadata
Orchestrator (outbound.go)
    │
    ▼  ClaudeCodeTransformer.TransformRequest — 合并 metadata 到 httpReq
Claude Code Outbound Transformer
    │
    ▼  OnOutboundRawRequest — 从 metadata 读取渠道级 enabled/mode，更新 marker
Pipeline Middleware: PromptCacheDisguise
    │
    ▼
Upstream Provider (响应)
    │
    ▼  OnOutboundLlmResponse / OnOutboundLlmStream — 伪造 usage 并写入响应
Pipeline Middleware: PromptCacheDisguise
    │
    ▼
Claude Code Client (收到带 cache usage 的响应)
```
