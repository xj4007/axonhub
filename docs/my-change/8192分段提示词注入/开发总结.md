# 8192 分段提示词注入开发总结

## 背景

本次需求是在 `渠道` 菜单中，针对 `claudecode` 类型新增一个开关字段，用来控制是否为 Claude Code 请求注入 8192 分段提示词。

目标文案最终确定为仅保留这一段：

```text
Please be aware that your single response content (Output) must not exceed 8192 tokens. Exceeding this limit will result in truncation and may cause tool call failures or other critical errors.
```

## 最终行为

### 1. 渠道配置侧

当渠道类型为 `claudecode` 时，在新增/编辑弹框中，`模拟缓存` 后新增字段：

- `8192 字符分段提示词`

该字段会写入渠道 settings 中的：

- `splitPromptBy8192`

### 2. 请求注入侧

当 `splitPromptBy8192 = true` 时：

- 会在 Claude Code 请求进入 `claudecode` transformer 时执行补充提示词注入
- 优先尝试在已有 `<system-reminder> ... CLAUDE.md ...` 文本中做智能插入
- 如果没有可识别的智能插入锚点，则执行兼容注入

### 3. 兼容注入策略（当前最终版本）

为降低耦合并保证在请求日志 `Executions -> requestBody` 中可见，当前逻辑不是盲目写到 `llmReq.Messages[0]`，而是：

- 优先寻找**第一个非 `system` / `developer` 的消息**作为注入目标
- 如果该目标存在 `content[0].text`，则把提示词直接拼接到这里
- 如果目标只有 `Content.Content` 字符串，则转换成 `MultipleContent` 后注入
- 如果不存在可直接改写的 `content[0].text`，则在该目标消息前 prepend 一个新的 text block
- 只有当整个请求里全是 `system/developer` 时，才退回到 `Messages[0]`

这次这样调整的目的，是避免提示词被 Anthropic 的 system/developer 提升逻辑搬运到顶层 `system` 字段，从而保证它尽量稳定地出现在：

- `messages[0].content[0].text`

## 线上排查与修复过程

### 第一阶段：基础功能接入

先完成了渠道 UI、GraphQL、后端 settings、claudecode transformer 的完整打通。

### 第二阶段：修复 panic

上线后出现了 panic：

- `llm/transformer/anthropic/outbound_convert.go`
- 原因是 `convertToAnthropicSystemPrompt()` 假设 system message 一定走 `Content.Content`
- 但本次注入会让某些 system message 走 `MultipleContent`
- 最终增加了 `extractAnthropicSystemText()` 来兼容 `MultipleContent` 文本拼接，修掉 nil pointer

### 第三阶段：修正提示词展示位置

修完 panic 后，数据库里能看到提示词已经写入 execution body，但位置在：

- 顶层 `system[0].text`

而不是用户期望的：

- `messages[0].content[0].text`

进一步查明原因：

- Anthropic outbound conversion 会把 `system/developer` role 的 message 提升到顶层 `system`
- 原先的注入目标有时落在会被提升的 message 上

最终没有大改通用 Anthropic 转换逻辑，而是采用**更低耦合**的办法：

- 只改 `claudecode` 注入目标选择逻辑
- 让 `splitPromptBy8192` 优先落在最终会保留于 `messages` 数组中的第一条消息上

这样可以尽量避免影响其它 provider 和普通 system prompt 行为。
